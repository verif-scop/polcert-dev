End-to-End Verified Polyhedral Compilation

PolCert checks loop optimizations proposed by an external optimizer and generates code only after the checks succeed. This guide explains what the compiler checks, what its main theorem guarantees, and where to read each part of the proof.

Three terms used throughout this guide. A statement instance is one execution of a statement at a particular tuple of loop indices. A schedule assigns integer coordinates that determine the order of those instances. The polyhedral model describes loop bounds, schedules, and memory accesses with integer equations and inequalities. Loop indices may be multiplied only by constants; this restriction is called affine.

Compiler Design

PolCert takes a bounded loop program and a choice of optimizations. An external optimizer may propose a new execution order, a split of an iteration domain, a tiling, or a parallel loop. PolCert checks each proposal. If a required check fails, compilation stops. An optional check may instead keep the last verified program, as specified by the chosen configuration.

What Each Stage Establishes

StageProposal or computationVerified result
Extraction Represent every statement execution as an integer point. Executing those points reproduces the source loop.
ISS Split one set of statement instances into smaller sets. Every original instance appears in exactly one part.
Affine scheduling Assign new ordering coordinates to the same instances. Any pair whose order changes is safe to exchange.
Tiling Group instances into blocks called tiles. Each instance appears once and the new block order is safe.
Loop generation Reconstruct ordinary loops from the checked model. The generated loops execute the checked statement instances.
Parallel annotation Mark one or more generated loops as parallel. Every possible parallel execution matches a valid sequential execution.
Scheduling and tiling require different checks. Scheduling changes only the order of a fixed set of instances. Tiling also changes their coordinates by adding a tile number and a position inside the tile. PolCert first proves that this coordinate change loses or duplicates nothing, then checks that the tile order is safe.

Reusable Instruction Interface

PolCert does not hard-code one instruction language into its validators. The INSTR interface supplies instruction semantics and memory effects. The polyhedral checks then reason about loop instances and those effects.

The text .loop frontend uses the lightweight model in SInstr.v. The examples below instead use typed scalar and array instructions from CInstr.v.

Correctness Guarantee

The main result is refinement: every behavior of an accepted target program is also allowed by the source program. Compilation may reject. If it returns a target, every target execution has a matching source execution from the same initial state. Their final states agree on every memory cell represented by the concrete model.

compile cfg source = Okk target

ParallelLoop.semantics target st st_target

implies

exists st_source, Loop.semantics source st st_source

and State.eq st_target st_source

For a parallel loop, iterations may be interleaved in any way that preserves the order inside each iteration. The compiler proves that all such executions are safe; the target language does not assume it.

These final proofs are short because they compose earlier results. The main work proves that the model matches the source, that each proposed transformation is legal, and that every parallel execution can be related to a sequential one.

Building the Polyhedral Model

Question
Does the model contain exactly the statement instances executed by the source loop?
Representation
Each instance records its statement, loop indices, parameters, instruction, and original order.
Proof idea
The proof follows the structure of the source loop. It identifies the instances produced by each iteration and joins them in source order. Every segment of the model's execution can then be mapped back to the source statement or loop that produced it.
Main theorem

Index-Set Splitting

Question
Does splitting one set of instances add, remove, or duplicate work?
Validator
Checks that every part has the expected form, belongs to the original set, covers it, and does not overlap another part.
Proof idea
Coverage ensures that every original instance remains; disjointness ensures that it appears only once. Joining the executions of all parts therefore reconstructs the original execution.
Main theorem
checked_iss_complete_cut_shape_validate_semantics_correct

Affine Scheduling

Question
Is it safe to run the same statement instances in the proposed new order?
Validator
Searches for two instances whose order is reversed even though their memory accesses make that exchange unsafe.
Proof idea
If no unsafe reversed pair exists, the new order can be obtained through safe exchanges of adjacent instances. Each exchange preserves the state, so the complete reordered execution does too.
Main theorem
AffineValidator.validate_correct
Selected reading
410 proof-body lines: conflict checking, list lifting, and validate_correct.
Source

Tiling and Permutable Bands

Question
Does the tiled program execute every original instance exactly once and in a safe order?
Validators
The first check relates an original loop index to its tile number and position inside that tile. The second checks that the selected dimensions form a permutable band: reordering them cannot reverse an unsafe pair.
Proof idea
Integer division and remainder map each original index to one tiled coordinate and back. This proves that tiling preserves the work. A separate argument proves that the checked tile order is safe for ordinary, two-level, and diamond layouts.
Main theorems
tiling_retiled_old_to_before_instance_correct_source; semantic_componentwise_permutable_implies_reordering_safe; checked_tiling_sourceb_complete_direct_band_check_correct
Selected reading
1,578 proof-body lines: 332 for the tiled-instance correspondence and 1,246 for ordinary-band order safety.
Source
TilingWitness.v, TilingRelation.v, TilingBandScheduleValidator.v, TilingBandDirectRuntime.v

Parallel Loops and Code Generation

Question
Does every possible execution of the generated parallel loop match a source execution?
Validator
Checks that instances from different iterations of each selected loop may safely exchange order.
Proof idea
The target model allows any interleaving that preserves the order inside each iteration. The proof maps every generated event back to a checked statement instance, then uses the validator result to reorder the interleaved execution into an equivalent sequential one. The existing sequential code-generation theorem finishes the argument.
Main theorems
annotated_codegen_many_raw_semantics_ordered; checked_annotated_codegen_many_correct_general_certified
Selected reading
725 proof-body lines: eligibility, generated-instance origin, interleaving serialization, cleanup, and the checked endpoint.
Source
ParallelLoop.v, ParallelValidator.v, RawCodegenOrigin.v, ParallelCodegenCorrect.v

The innermost-only parallel mode reuses the same independence check and additionally requires the selected generated loop to be innermost. Its target still has ordinary parallel-loop semantics.

Constant Unrolling and Unroll-and-Jam

Question
Do the supported loop-unrolling rewrites preserve execution?
Transformations
Constant unrolling expands a sequential loop with fixed bounds. Block unrolling groups several iterations. Jam then fuses corresponding inner loops when the required exchanges are safe.
Proof idea
The main blocks and any leftover iterations cover the original range exactly. The jam check proves that the grouped loop bodies can be exchanged as required before they are fused.
Main theorems
LoopUnroll.const_unroll_correct; LoopUnroll.block_unroll_correct; VerifiedLoopPostpass.apply_checked_unrolljam_correct
Source
LoopUnroll.v, LoopJamBridge.v, VerifiedLoopPostpass.v

Scope and Boundaries

The theorem covers accepted structured-loop compilations to the generated ParallelLoop model. It does not cover:

  • the optimizer's search algorithm, although its proposals are checked;
  • text parsing and printing;
  • the external C compiler, runtime system, and hardware;
  • transformations that change storage or the set of executed statement instances.

PolCert may also reject a legal optimization that its checks cannot establish. Acceptance is proved correct; acceptance of every legal optimization is not claimed.
