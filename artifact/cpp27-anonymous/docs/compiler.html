Compiler

PolCert compiles a bounded affine loop through a polyhedral intermediate representation. Verified passes perform representation changes. A validator accepts an optimizer proposal only after checking its correctness conditions.

The Polyhedral Model

PolCert represents each execution of a loop statement by its loop indices. For example, one execution of A[i][j] = B[i][j] + 1 is identified by the integer point (i,j). Affine inequalities describe which points execute, affine access functions describe which array cells they read and write, and a schedule assigns coordinates that order the points.

Loop optimization changes the schedule or introduces new coordinates. It must preserve every original statement instance and respect any memory dependence that constrains execution order. The source and intermediate representations are defined in Loop.v and PolyLang.v; parallel output uses ParallelLoop.v.

Executable Entry Point

The polopt executable accepts a structured .loop file and Pluto-compatible optimization options. The parser and elaborator construct the source Loop program. Pluto then proposes schedules, tiling phases, ISS data, and concurrency hints. Route selection passes those proposals to the corresponding extracted validators and verified compiler functions.

The end-to-end theorem begins at the structured source Loop program, after parsing and elaboration. Pluto and the surrounding OCaml wrapper may choose a route or produce a proposal, but they cannot make a failed validator return an accepted target.

Domain strengthening Adds parameter and enclosing-loop guards that are already implied by the extracted domains. The added constraints are redundant, so the set and order of statement instances are unchanged. StrengthenDomain.v
Index-set splitting (optional) Replaces a statement domain with a proposed collection of subdomains. The checker establishes exact coverage, pairwise disjointness, and preservation of the statement payload. ISSValidator.v, ISSValidatorCorrect.v
Affine scheduling (optional) Replaces schedule coordinates; this represents interchange, skewing, fusion, fission, and related affine changes. For every pair whose order changes, the validator proves that exchanging the pair is safe. AffineValidator.v, Validator.v

Parallel eligibility (optional) Checks one or more proposed schedule dimensions in the current-coordinate view before annotated loop generation. Optimizer output is always a proposal. A mandatory check must succeed before its route returns a target. ISS inference is optional: if it produces no valid split, compilation continues from the preceding verified intermediate program.

Running Example

The pointwise example begins with a two-dimensional iteration domain 0 <= i0 < N, 0 <= i1 < M. In the output, i0 and i1 enumerate tiles, while i2 and i3 enumerate points inside each tile. Integer division maps every source point to exactly one tile, and the bounded point loops recover the original index values.

Typed Input Program

context(N, M);

for i0 in range(0, N) {
  for i1 in range(0, M) {
    A[i0][i1] = B[i0][i1] + 1;
  }
}

Accepted Verified Program

context(N, M);

if ((1 <= N && 1 <= M)) {
  for i0 in range(0, ((N + 31) / 32)) {
    for i1 in range(0, ((M + 31) / 32)) {
      for i2 in range(max(0, (32 * i0)), min(N, ((32 * i0) + 32))) {
        parallel for i3 in range(max(0, (32 * i1)), min(M, ((32 * i1) + 32))) {
          A[i2][i3] = B[i2][i3] + 1;
        }
      }
    }
  }
}

The parallel check establishes that different i3 iterations do not conflict. The complete case page shows the exact generated bounds and matching execution results.

Supported Transformations and Cleanup Passes

Transformation Effect Acceptance condition Implementation
Affine scheduling Changes loop order and shape; covers interchange, skewing, fusion, and fission. Every statement pair whose order reverses may safely exchange. AffineValidator.v
Index-set splitting (ISS) Splits one statement domain into disjoint pieces, which may then receive different schedules. The pieces preserve the statement and form an exact partition of the source domain. ISSValidator.v, ISSWitness.v
Ordinary tiling Adds rectangular tile coordinates and intra-tile point coordinates. The candidate realizes every source instance exactly once and the tiled band has a safe order. TilingRelation.v, TilingBandScheduleValidator.v
Two-level tiling Adds two nested levels of tile coordinates. Both levels satisfy the instance-mapping and band-order obligations for a recognized layout. TilingBandDirectRuntime.v, TilingBandMixedSecondValidator.v
Diamond tiling Uses coupled tile coordinates to form wavefront-shaped tiles; full-diamond routes use the same checked tiling boundary. The candidate satisfies the same exact instance mapping and band-order obligations as other accepted tiling layouts. TilingBandDirectRuntime.v, PolOpt.v
Post-tiling affine scheduling Reschedules the tiled program, including its intra-tile loops. The affine validator accepts the new schedule relative to the tiled program. ParallelPolOpt.v, Validator.v
Parallelization Marks one or more generated loop dimensions as parallel, allowing their iterations to interleave. Statement instances from distinct iterations at each selected dimension may exchange order. ParallelValidator.v, ParallelCodegenCore.v
Innermost vector annotation Uses the parallel certificate for an innermost loop and records the more restricted vector mode. The parallel check succeeds and the selected generated loop is innermost. ParallelCodegenCore.v, ParallelCodegenCorrect.v
Constant-bound unrolling Expands sequential loops whose complete iteration range is known. The expanded statements cover the original range exactly. Parallel loop annotations are retained and are not themselves unrolled. LoopUnroll.v, VerifiedParallelCompilerConfig.v
Block and remainder unrolling Executes full blocks of a chosen factor and handles the remaining iterations separately. The block and remainder ranges partition the original loop range. LoopUnroll.v
Unroll-and-jam Block-unrolls an outer loop and fuses corresponding inner loops. The unrolling is exact, and the validator accepts every exchange introduced by the fusion. LoopJamValidator.v, LoopJamBridge.v, LoopJamLower.v
Singleton-loop and expression cleanup Removes one-iteration loops and simplifies generated loop syntax. The cleaned loop has the same executions as the generated loop. LoopSingletonCleanup.v, LoopCleanup.v, ParallelLoop.v

Reusable Instruction Interface

The validators reason about loop instances and memory effects through the INSTR interface. They do not require instructions to be empty or tied to one frontend. The text .loop examples use a lightweight instruction model. Additional examples instantiate typed scalar and array operations in CTypedLoopSamples.v.
