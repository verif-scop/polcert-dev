Evaluation

In addition to the formal verification, this artifact includes functional, executable, performance, and rejection tests for the extracted compiler. They inspect the generated loops and run accepted programs to check their results and performance.

Functional Tests by Transformation

The test catalog records the input, expected behavior, observed transformation, and accepted output or rejection for each case. Tests with source and optimized Loop programs display the programs side by side.

Transformation Tested behavior Evidence
Affine scheduling Schedule changes, including loop fusion and fission, appear in the accepted target; illegal reorderings are rejected. Affine scheduling
Index-set splitting The output partitions statement instances into the proposed regions and remains compatible with later transformations. Index-set splitting
Tiling Ordinary, two-level, and diamond tiling produce the expected tile and point loops through the checked tiling route. ordinary, two-level, and diamond
Parallelization Accepted dimensions become parallel loops; dependent or non-certifiable dimensions do not. Parallel loops
Generated-loop postpasses Constant unrolling, block unrolling, and unroll-and-jam change the output only when their checks succeed. Loop postpasses
Composed pipelines Transformation combinations pass through the complete compiler, including typed instruction examples and driver option routes. Composed pipelines

Program Execution

For each saved, executable before/after Loop pair, the harness compiles and runs both programs with the same parameters and input initialization, then compares their results. Each case page reports the parameters, repetitions, OpenMP thread count when relevant, and comparison result.

A separate whole-C campaign compared the unoptimized and accepted programs. Each linked kernel page records the complete before/accepted program pair, selected compiler route, matching execution result, and measured runtime.

Recorded Configuration

The campaign used the perf parameter tier, one baseline run and one accepted-output run per candidate, and cc -O3 -std=c99. Parallel outputs were compiled with -fopenmp and run with four threads. Each kernel page records its parameter values and selected polopt options. 

docker build -f environment/Dockerfile -t polcert-artifact .
docker run --rm polcert-artifact performance

The complete reproduction configuration and route selection are included with the report. Runtime values should be remeasured on the reviewer's Docker host.

Rejected Optimizer Proposals

Negative tests submit candidates that violate schedule legality, tiling realization, parallel-dimension eligibility, or compiler-route requirements. PolCert must reject such candidates rather than emit an unchecked optimized loop.

The rejection report states, for each case, the violated condition, the optimizer source of the proposal, and whether PolCert rejected the complete output or kept a certified subset. The focused cases include confirmed Pluto miscompilations, an unsafe optimizer control input, a historical fork regression, and a non-certifiable parallel hint. The linked bug-report draft provides reproduction commands and root-cause analysis.
